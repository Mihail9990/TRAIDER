# AI Impulse Trader v1.0

## Главная спецификация проекта

**Статус:** DRAFT

------------------------------------------------------------------------

# Назначение документа

Настоящий документ является главным документом проекта AI Impulse Trader
v1.0.

Любая реализация кода должна соответствовать требованиям данного
документа.

Если код противоречит спецификации, правильной считается спецификация.

------------------------------------------------------------------------

# Цель проекта

Создать надежный торговый движок для Capital.com, реализующий заранее
определенную стратегию торговли с возможностью:

-   безопасной автоматической работы;
-   восстановления после сбоев;
-   последовательного сопровождения торгового цикла;
-   перехода SIMULATOR → DEMO → REAL.

------------------------------------------------------------------------

# Основные принципы

REQ-001. Одновременно существует только один активный торговый цикл.

REQ-002. Каждый модуль имеет только одну ответственность.

REQ-003. Каждый тип данных имеет один Source of Truth.

REQ-004. Все торговые расчеты выполняет только Formula Engine.

REQ-005. Любое действие подтверждается перед переходом к следующему
этапу.

REQ-006. После любого сбоя проект должен иметь возможность
восстановления.

REQ-007. Архитектура изменяется только после изменения спецификации.

# 01_CONFIG.md

# Конфигурация проекта

## Назначение

Документ определяет все настраиваемые параметры AI Impulse Trader v1.0,
правила их использования и ограничения изменения.

------------------------------------------------------------------------

## Общие правила

-   Все параметры загружаются из `config.py`.
-   При запуске нового Cycle создается неизменяемая копия в
    CycleSettings.
-   Изменение параметров во время активного Cycle запрещено, если иное
    не указано.

------------------------------------------------------------------------

## Основные параметры

### Broker

-   MODE = SIMULATOR \| DEMO \| REAL
-   SYMBOL
-   POSITION_SIZE

### Strategy

-   BASE_TAKE_PROFIT
-   STOP_LOSS_DISTANCE
-   MAX_SCENARIO = 9
-   MAX_RETRY
-   ANALYZE_INTERVAL

### Trading Costs

-   SPREAD
-   COMMISSION
-   SLIPPAGE

### Recovery

-   ENABLE_RECOVERY
-   SNAPSHOT_AUTOSAVE
-   RETRY_DELAY

### Logging

-   LOG_LEVEL
-   LOG_TO_FILE
-   LOG_ROTATION

### Notifications

-   ENABLE_NOTIFICATIONS
-   TELEGRAM_ENABLED (зарезервировано для будущих версий)

------------------------------------------------------------------------

## Правила изменения

REQ-CONF-001

Параметры проходят проверку при запуске приложения.

REQ-CONF-002

Недопустимые значения запрещают старт системы.

REQ-CONF-003

Cycle использует только собственную копию настроек.

REQ-CONF-004

Изменения config.py влияют только на новые Cycle.

------------------------------------------------------------------------

## Recovery

После восстановления используются параметры, сохраненные в
CycleSettings, а не текущий config.py.

------------------------------------------------------------------------

## Критерии приемки

✓ Все параметры валидируются.

✓ Cycle использует неизменяемую копию настроек.

✓ Изменения конфигурации не влияют на уже активный Cycle.

# 01_LIFECYCLE.md

# Жизненный цикл торгового цикла

## Назначение

Документ определяет полный жизненный цикл одного торгового цикла AI
Impulse Trader.

Торговый цикл начинается после подтверждения Entry Filter и
заканчивается архивированием результатов.

Одновременно может существовать только один активный Cycle.

------------------------------------------------------------------------

# Состояния

STATE-001 CREATED Создан объект Cycle.

STATE-002 WAIT_ENTRY Ожидание сигнала Entry Filter.

STATE-003 PREPARE Подготовка к открытию позиций.

STATE-004 OPENING Открытие LONG и SHORT.

STATE-005 VERIFY_OPEN Проверка успешного открытия.

STATE-006 RUNNING Основной режим сопровождения стратегии.

STATE-007 RECOVERY Восстановление после ошибки или перезапуска.

STATE-008 FINISHING Завершение торгового цикла.

STATE-009 FINISHED Цикл завершен.

STATE-010 ARCHIVED Цикл сохранен в историю.

------------------------------------------------------------------------

# Последовательность

WAIT_ENTRY ↓

PREPARE ↓

OPENING ↓

VERIFY_OPEN ↓

RUNNING ↓

FINISHING ↓

FINISHED ↓

ARCHIVED

RECOVERY может быть вызван из любого состояния до FINISHED.

------------------------------------------------------------------------

# Описание состояний

## WAIT_ENTRY

Назначение: Ожидание разрешения Entry Filter.

Разрешено: - получение рыночных данных; - анализ рынка.

Запрещено: - открытие позиций; - создание Trigger; - изменение Snapshot.

Переход: WAIT_ENTRY -\> PREPARE.

------------------------------------------------------------------------

## PREPARE

Выполняется:

-   создание Cycle;
-   создание Snapshot;
-   копирование настроек;
-   проверка подключения;
-   проверка отсутствия активного цикла;
-   проверка брокера.

При успешном завершении: PREPARE -\> OPENING.

------------------------------------------------------------------------

## OPENING

Последовательность:

1.  открыть LONG;
2.  подтвердить LONG;
3.  открыть SHORT;
4.  подтвердить SHORT;
5.  сохранить реальные цены исполнения;
6.  передать данные Formula Engine.

Если подтверждение отсутствует --- переход в RECOVERY.

------------------------------------------------------------------------

## VERIFY_OPEN

Проверить:

-   LONG открыт;
-   SHORT открыт;
-   цены сохранены;
-   позиции соответствуют настройкам;
-   Snapshot существует.

Только после этого: VERIFY_OPEN -\> RUNNING.

------------------------------------------------------------------------

## RUNNING

Основное состояние.

В нем выполняются:

-   Scenario 1;
-   Universal Reentry Scenario (2--8);
-   Scenario 9.

Все изменения состояния должны подтверждаться.

------------------------------------------------------------------------

## RECOVERY

Вызывается при:

-   потере сети;
-   ошибке API;
-   аварийном завершении;
-   перезапуске программы.

Recovery обязан определить последнее подтвержденное действие и
продолжить выполнение с него.

Recovery запрещено изменять стратегию.

------------------------------------------------------------------------

## FINISHING

Выполняется:

-   завершение последних действий;
-   сохранение статистики;
-   очистка временных данных.

------------------------------------------------------------------------

## FINISHED

Торговые действия запрещены.

Допускается только чтение информации.

------------------------------------------------------------------------

## ARCHIVED

Цикл сохраняется в историю.

После архивирования изменения запрещены.

------------------------------------------------------------------------

# Обязательные требования

REQ-LC-001 Только один активный Cycle.

REQ-LC-002 Каждый переход подтверждается.

REQ-LC-003 После каждого подтвержденного этапа состояние доступно
Recovery.

REQ-LC-004 Новый цикл запрещен до ARCHIVED предыдущего.

------------------------------------------------------------------------

# Критерии приемки

✓ Новый цикл не стартует при активном предыдущем.

✓ После открытия обеих позиций выполняется VERIFY_OPEN.

✓ Любой сбой переводит систему в RECOVERY.

✓ После ARCHIVED цикл больше не изменяется.

Статус документа: DRAFT

Следующий документ: 02_ENTRY_FILTER.md

# 01_MODELS.md

# Модели данных проекта

## Назначение

Документ описывает все основные структуры данных AI Impulse Trader v1.0.
Каждая модель имеет единственную ответственность и строго определенный
жизненный цикл.

------------------------------------------------------------------------

# Общие требования

REQ-MD-001\
Все модели должны быть сериализуемыми.

REQ-MD-002\
Все модели должны поддерживать восстановление после перезапуска.

REQ-MD-003\
Изменение моделей допускается только через ответственный модуль.

------------------------------------------------------------------------

# Cycle

Назначение: Хранит полное состояние торгового цикла.

Основные поля: - cycle_id - state - current_scenario - created_at -
finished_at - long_position - short_position - snapshot_id -
statistics_id

Изменяется только Cycle Manager.

------------------------------------------------------------------------

# Position

Назначение: Описывает одну торговую позицию.

Поля: - side - entry_price - volume - stop_loss - take_profit - status -
broker_order_id

Изменяется только Order Manager.

------------------------------------------------------------------------

# Trigger

Назначение: Описывает Trigger-ордер.

Поля: - trigger_id - side - trigger_price - volume - status -
broker_order_id

Изменяется только Trigger Manager.

------------------------------------------------------------------------

# Snapshot

Назначение: Неизменяемый снимок начального состояния цикла.

Содержит: - цены входа - настройки цикла - параметры стратегии -
идентификатор цикла

После создания изменение запрещено.

------------------------------------------------------------------------

# CycleSettings

Назначение: Копия параметров config.py для конкретного цикла.

Изменение во время активного цикла запрещено.

------------------------------------------------------------------------

# Statistics

Назначение: Итоговая информация завершенного цикла.

Содержит: - итог прибыли/убытка - количество Reentry - длительность -
номер последнего сценария - причины завершения

После сохранения изменение запрещено.

------------------------------------------------------------------------

# Связи моделей

Cycle ├── LONG Position ├── SHORT Position ├── Trigger ├── Snapshot ├──
CycleSettings └── Statistics

------------------------------------------------------------------------

# Критерии приемки

✓ Все модели имеют одного владельца.

✓ Snapshot неизменяем.

✓ Statistics формируется только после завершения цикла.

✓ Каждая модель имеет уникальный идентификатор.

Статус документа: DRAFT

# 01_STRATEGY.md

# Торговая стратегия AI Impulse Trader v1.0

## Назначение

Документ описывает общую логику работы торгового движка до детализации
отдельных сценариев.

Все последующие документы со сценариями являются продолжением данного
документа.

------------------------------------------------------------------------

# Цель стратегии

Стратегия предназначена для сопровождения одного торгового цикла, в
рамках которого одновременно используются позиции LONG и SHORT.

Основные задачи:

-   контролируемое сопровождение цикла;
-   компенсация убытков повторными входами;
-   централизованный расчет целей через Formula Engine;
-   безопасное завершение цикла.

------------------------------------------------------------------------

# Общая последовательность

1.  Entry Filter разрешает старт.
2.  Cycle Manager создает Cycle.
3.  Создается Snapshot.
4.  Открываются LONG и SHORT.
5.  Выполняется VERIFY_OPEN.
6.  Цикл переходит в RUNNING.
7.  Выполняются сценарии стратегии.
8.  После завершения формируется Statistics.
9.  Cycle архивируется.

------------------------------------------------------------------------

# Основные правила

REQ-STR-001

Одновременно выполняется только один Cycle.

REQ-STR-002

Все расчеты выполняет Formula Engine.

REQ-STR-003

Любое действие подтверждается брокером.

REQ-STR-004

Каждый переход состояния фиксируется.

REQ-STR-005

После сбоя используется Recovery Manager.

------------------------------------------------------------------------

# Роль сценариев

Сценарии определяют реакцию системы на изменения состояния позиций.

В версии 1.0 используются:

-   Scenario 1;
-   Universal Reentry (основа сценариев 2--8);
-   Scenario 9;
-   Завершение цикла.

Каждый сценарий начинается только после успешного завершения
предыдущего.

------------------------------------------------------------------------

# Взаимодействие модулей

Entry Filter → Cycle Manager → Order Manager → Capital API → Formula
Engine → Trigger Manager → Cycle Manager

Recovery Manager может быть вызван на любом этапе до завершения цикла.

------------------------------------------------------------------------

# Ограничения

Запрещено:

-   открывать новый Cycle до завершения предыдущего;
-   выполнять торговые расчеты вне Formula Engine;
-   изменять Snapshot;

# Модель Cycle

## Назначение

Cycle представляет один полный торговый цикл. Все остальные объекты
проекта связаны с конкретным экземпляром Cycle.

------------------------------------------------------------------------

## Владелец модели

Единственный модуль, имеющий право изменять Cycle --- Cycle Manager.

Другие модули могут только читать данные либо передавать события Cycle
Manager.

------------------------------------------------------------------------

## Основные поля

-   cycle_id
-   state
-   current_scenario
-   created_at
-   finished_at
-   long_position_id
-   short_position_id
-   snapshot_id
-   settings_id
-   statistics_id
-   recovery_required
-   last_confirmed_step

------------------------------------------------------------------------

## Жизненный цикл

CREATED → WAIT_ENTRY → PREPARE → OPENING → VERIFY_OPEN → RUNNING →
FINISHING → FINISHED → ARCHIVED

Переходы выполняются только Cycle Manager.

------------------------------------------------------------------------

## Правила изменения

REQ-CYCLE-001 cycle_id неизменяем после создания.

REQ-CYCLE-002 state изменяется только последовательными переходами.

REQ-CYCLE-003 current_scenario увеличивается только после успешного
завершения сценария.

REQ-CYCLE-004 finished_at устанавливается только при завершении цикла.

REQ-CYCLE-005 last_confirmed_step обновляется после каждого
подтвержденного действия.

------------------------------------------------------------------------

## Связанные объекты

Cycle содержит ссылки на:

-   LONG Position
-   SHORT Position
-   Snapshot
-   Trigger(ы)
-   CycleSettings
-   Statistics

------------------------------------------------------------------------

## Recovery

Recovery Manager использует Cycle как основной объект восстановления.

После восстановления выполнение продолжается с last_confirmed_step.

------------------------------------------------------------------------

## Запрещено

-   создавать второй активный Cycle;
-   изменять cycle_id;
-   изменять завершенный Cycle;
-   пропускать состояния жизненного цикла.

------------------------------------------------------------------------

## Критерии приемки

✓ Один активный Cycle.

✓ Все изменения выполняет Cycle Manager.

✓ После ARCHIVED объект доступен только для чтения.

✓ Recovery восстанавливает Cycle без потери состояния.

# 02_ENTRY_FILTER.md

# Entry Filter

## Назначение

Entry Filter --- единственный модуль, имеющий право разрешить начало
нового торгового цикла.

Entry Filter не открывает позиции, не выполняет расчеты и не работает с
ордерами. Его задача --- принять решение: можно ли запускать новый
Cycle.

------------------------------------------------------------------------

## Ответственность

-   Анализировать входные рыночные данные.
-   Проверять готовность системы.
-   Проверять отсутствие активного цикла.
-   Передавать разрешение Cycle Manager.

------------------------------------------------------------------------

## Source of Truth

Источник истины для условий входа --- Entry Filter.

После выдачи разрешения управление передается Cycle Manager.

------------------------------------------------------------------------

## Входные данные

-   Текущие Bid/Ask.
-   Данные Market Data.
-   Настройки config.py.
-   Состояние Cycle Manager.
-   Статус брокера.

------------------------------------------------------------------------

## Предварительные проверки

REQ-EF-001 Нет активного торгового цикла.

REQ-EF-002 Подключение к брокеру активно.

REQ-EF-003 Получаются актуальные рыночные данные.

REQ-EF-004 Нет активного Recovery.

REQ-EF-005 Настройки успешно загружены.

Если хотя бы одна проверка не пройдена --- старт цикла запрещен.

------------------------------------------------------------------------

## Алгоритм

1.  Получить новые рыночные данные.
2.  Проверить системные условия.
3.  Выполнить пользовательскую стратегию фильтра входа.
4.  Если условия не выполнены --- продолжить ожидание.
5.  Если условия выполнены --- отправить Cycle Manager разрешение
    START_CYCLE.

Entry Filter не должен создавать Cycle самостоятельно.

------------------------------------------------------------------------

## Запрещено

-   открывать LONG;
-   открывать SHORT;
-   создавать Trigger;
-   изменять Snapshot;
-   выполнять торговые расчеты;
-   менять номер сценария.

------------------------------------------------------------------------

## Взаимодействие

Получает данные от: - Market Data; - Config.

Передает решение: - Cycle Manager.

------------------------------------------------------------------------

## Обработка ошибок

При отсутствии данных рынка: - повторить получение.

При потере соединения: - ожидать восстановления.

При ошибке конфигурации: - запретить запуск цикла.

------------------------------------------------------------------------

## Recovery

После восстановления Entry Filter начинает анализ заново.

Если Cycle уже существует, Entry Filter не запускает новый цикл.

------------------------------------------------------------------------

## Критерии приемки

✓ Не запускает второй цикл.

✓ Не открывает позиции.

✓ Не выполняет расчеты.

✓ Передает только разрешение на запуск.

Статус документа: DRAFT

Следующий документ: 03_CYCLE_MANAGER.md

## Назначение

Сценарий 1 описывает реакцию системы на первое подтвержденное
срабатывание Stop Loss одной из первоначально открытых позиций.

------------------------------------------------------------------------

## Цель

-   Зафиксировать закрытие позиции.
-   Создать Trigger на цену входа закрытой стороны.
-   Сохранить непрерывность торгового цикла.
-   Подготовить систему к возможному повторному входу.

------------------------------------------------------------------------

## Условия запуска

Обязательны все условия:

-   Cycle находится в состоянии RUNNING.
-   LONG и SHORT открыты и подтверждены.
-   Один Stop Loss подтвержден брокером.
-   Второй ордер остается активным.

------------------------------------------------------------------------

## Последовательность

1.  Order Manager получает подтверждение Stop Loss.
2.  Position переводится в CLOSED.
3.  Cycle Manager фиксирует событие.
4.  Trigger Manager создает Trigger на исходную цену входа закрытой
    стороны.
5.  Брокер подтверждает создание Trigger.
6.  Formula Engine пересчитывает параметры повторного входа.
7.  Order Manager обновляет TP/SL, если требуется.
8.  Cycle Manager завершает Scenario 1.
9.  current_scenario увеличивается до следующего.

------------------------------------------------------------------------

## Изменяемые данные

-   Position.status
-   Trigger
-   current_scenario
-   last_confirmed_step

------------------------------------------------------------------------

-   Snapshot
-   cycle_id
-   initial entry prices
-   CycleSettings

------------------------------------------------------------------------

## Подтверждения

Обязательны подтверждения:

-   закрытия позиции;
-   создания Trigger;
-   применения изменений TP/SL (если были);
-   завершения сценария.

Без подтверждения переход запрещен.

------------------------------------------------------------------------

## Recovery

Если произошел сбой:

-   определить последнее подтвержденное действие;
-   восстановить Position;
-   восстановить Trigger;
-   не повторять подтвержденные операции;
-   продолжить выполнение сценария.

------------------------------------------------------------------------

## Условия завершения

Scenario 1 считается завершенным только если:

-   Stop Loss подтвержден;
-   Trigger подтвержден;
-   состояние Cycle обновлено;
-   current_scenario увеличен.

------------------------------------------------------------------------

## Критерии приемки

✓ Trigger создается только после подтвержденного Stop Loss.

✓ Trigger создается на исходную цену входа закрытой стороны.

# 03_CYCLE_MANAGER.md

# Cycle Manager

## Назначение

Cycle Manager является центральным координатором жизненного цикла
торгового цикла. Он не выполняет торговые расчеты и не взаимодействует с
API брокера напрямую.

------------------------------------------------------------------------

## Ответственность

-   создание объекта Cycle;
-   изменение состояния Cycle;
-   контроль последовательности этапов;
-   запуск связанных модулей;
-   запрет недопустимых переходов;
-   завершение и архивирование цикла.

------------------------------------------------------------------------

## Source of Truth

Источник истины для состояния торгового цикла --- Cycle Manager.

------------------------------------------------------------------------

## Входные данные

-   Разрешение START_CYCLE от Entry Filter;
-   результаты Formula Engine;
-   подтверждения Order Manager;
-   события Trigger Manager;
-   события Recovery Manager.

------------------------------------------------------------------------

## Выходные данные

-   команды запуска этапов;
-   изменение состояния Cycle;
-   завершение цикла;
-   сохранение статистики.

------------------------------------------------------------------------

## Основной алгоритм

1.  Получить START_CYCLE.
2.  Создать Cycle.
3.  Перевести состояние в PREPARE.
4.  Дождаться Snapshot.
5.  Запустить OPENING.
6.  После VERIFY_OPEN перевести в RUNNING.
7.  Управлять переходами сценариев.
8.  После завершения перевести в FINISHING.
9.  Сохранить статистику.
10. Перевести в FINISHED.
11. Архивировать Cycle.

------------------------------------------------------------------------

## Допустимые переходы

CREATED -\> WAIT_ENTRY

WAIT_ENTRY -\> PREPARE

PREPARE -\> OPENING

OPENING -\> VERIFY_OPEN

VERIFY_OPEN -\> RUNNING

RUNNING -\> FINISHING

FINISHING -\> FINISHED

FINISHED -\> ARCHIVED

Из любого состояния до FINISHED допускается переход в RECOVERY.

------------------------------------------------------------------------

## Запрещено

-   открывать позиции;
-   изменять TP/SL;
-   выполнять расчеты;
-   создавать Trigger;
-   запускать второй Cycle.

------------------------------------------------------------------------

## Взаимодействие

Получает: - Entry Filter - Formula Engine - Order Manager - Trigger
Manager - Recovery Manager

Передает: - команды Order Manager; - смену этапов; - завершение цикла.

------------------------------------------------------------------------

## Обработка ошибок

Если подтверждение этапа отсутствует: - ожидать; - выполнить повтор
согласно Retry Policy; - при невозможности завершения передать
управление Recovery Manager.

------------------------------------------------------------------------

## Recovery

После восстановления продолжить работу с последнего подтвержденного
состояния.

Запрещено создавать новый Cycle, если предыдущий восстановлен.

------------------------------------------------------------------------

## Критерии приемки

✓ Один активный Cycle.

✓ Все переходы последовательны.

✓ Запрещены пропуски состояний.

✓ После ARCHIVED цикл неизменяем.

Статус документа: DRAFT

## Назначение

-   Уведомления не влияют на выполнение стратегии.
-   Неудачная отправка уведомления не должна останавливать торговый
    цикл.
-   Каждое уведомление содержит время, уровень и описание события.

-   запуск приложения;
-   запуск нового Cycle;
-   завершение Cycle;
-   переход между сценариями.

-   повторная попытка запроса;
-   задержка подтверждения брокера;
-   переход в Recovery.

### Ошибки (ERROR)

-   ошибка API;
-   невозможность выполнить действие;
-   ошибка восстановления.

### Критические (CRITICAL)

-   переход в Scenario 9;
-   невозможность безопасного восстановления;
-   остановка автоматической торговли.

------------------------------------------------------------------------

Поддерживаются отдельные переключатели:

-   INFO
-   WARNING
-   ERROR
-   CRITICAL

Каждое уведомление должно содержать:

-   timestamp;
-   level;
-   cycle_id (если есть);
-   module;
-   message.

------------------------------------------------------------------------

Архитектура должна позволять в будущем подключить Telegram как внешний
канал без изменения торгового ядра.

------------------------------------------------------------------------

## Recovery

Все события Recovery сопровождаются отдельными уведомлениями уровня
WARNING, ERROR или CRITICAL.

------------------------------------------------------------------------

## Критерии приемки

✓ Все критические события сопровождаются уведомлением.

✓ Сбой отправки уведомления не влияет на торговый процесс.

✓ Поддерживается раздельное включение категорий.

# Модель Position

## Назначение

Position описывает одну торговую позицию внутри Cycle. В каждом цикле
существуют ровно две позиции: LONG и SHORT.

------------------------------------------------------------------------

## Владелец модели

Изменять Position имеет право только Order Manager на основании
подтвержденных действий брокера и команд Cycle Manager.

------------------------------------------------------------------------

## Основные поля

-   position_id
-   cycle_id
-   side (LONG / SHORT)
-   status
-   volume
-   entry_price_requested
-   entry_price_filled
-   stop_loss
-   take_profit
-   broker_position_id
-   created_at
-   closed_at
-   reentry_count
-   accumulated_reentry_costs

------------------------------------------------------------------------

## Возможные состояния

CREATED

↓

OPENING

↓

OPEN

↓

CLOSING

↓

CLOSED

Дополнительно:

ERROR --- используется только до завершения Recovery.

------------------------------------------------------------------------

## Правила изменения

REQ-POS-001

Цена исполнения записывается только после подтверждения брокера.

REQ-POS-002

TP и SL изменяются только по расчетам Formula Engine.

REQ-POS-003

reentry_count увеличивается только после подтвержденного повторного
входа.

REQ-POS-004

closed_at устанавливается только после подтвержденного закрытия позиции.

REQ-POS-005

Статус изменяется только последовательно.

------------------------------------------------------------------------

## Reentry

После исполнения Trigger позиция считается повторно открытой.

При этом:

-   сохраняется связь с Cycle;
-   увеличивается reentry_count;
-   Formula Engine пересчитывает CURRENT_TARGET и REENTRY_COSTS;
-   Order Manager обновляет TP/SL после подтверждения.

------------------------------------------------------------------------

## Взаимодействие

Получает изменения от:

-   Order Manager
-   Formula Engine
-   Trigger Manager (через события)

Используется:

-   Cycle Manager
-   Recovery Manager
-   Statistics

------------------------------------------------------------------------

## Запрещено

-   изменять Position вручную;
-   менять TP/SL без Formula Engine;
-   менять статус без подтверждения брокера;
-   изменять CLOSED Position.

------------------------------------------------------------------------

## Recovery

Recovery Manager обязан:

-   сверить Position с брокером;
-   восстановить фактический статус;
-   восстановить цены исполнения;
-   продолжить выполнение с последнего подтвержденного шага.

------------------------------------------------------------------------

## Критерии приемки

✓ Каждая Position принадлежит одному Cycle.

✓ LONG и SHORT имеют независимые состояния.

✓ TP/SL соответствуют последнему расчету Formula Engine.

✓ Повторный вход корректно увеличивает reentry_count.

# 03_UNIVERSAL_REENTRY.md

# Universal Reentry Algorithm

## Назначение

Документ описывает единый алгоритм повторного входа, используемый
сценариями 2--8. Все сценарии используют одинаковую последовательность
действий, различаясь только стороной (LONG/SHORT) и накопленными
расчетными значениями.

------------------------------------------------------------------------

## Цель

-   Выполнить безопасный повторный вход.
-   Сохранить целостность торгового цикла.
-   Компенсировать предыдущие потери.
-   Передать обновленные параметры Formula Engine.

------------------------------------------------------------------------

## Условия запуска

Алгоритм запускается только если:

-   Trigger исполнен и подтвержден брокером;
-   Cycle находится в RUNNING;
-   Scenario 1 завершен;
-   Position повторно открыта.

------------------------------------------------------------------------

## Последовательность

1.  Trigger Manager подтверждает EXECUTED.
2.  Order Manager сохраняет фактическую цену исполнения.
3.  Position увеличивает `reentry_count`.
4.  Formula Engine пересчитывает:
    -   REENTRY_COSTS;
    -   CURRENT_TARGET;
    -   TP;
    -   SL (если стратегия требует изменения).
5.  Order Manager применяет новые параметры.
6.  Брокер подтверждает изменения.
7.  Cycle Manager завершает текущий сценарий.
8.  `current_scenario` увеличивается на 1.

------------------------------------------------------------------------

## Общие правила

REQ-UR-001

Каждый подтвержденный повторный вход увеличивает накопленные
REENTRY_COSTS.

REQ-UR-002

CURRENT_TARGET всегда рассчитывается заново Formula Engine.

REQ-UR-003

Повторный вход не изменяет Snapshot.

REQ-UR-004

Все изменения выполняются только после подтверждений брокера.

------------------------------------------------------------------------

## Изменяемые данные

-   Position.reentry_count
-   Position.take_profit
-   REENTRY_COSTS
-   CURRENT_TARGET
-   current_scenario
-   last_confirmed_step

------------------------------------------------------------------------

## Неизменяемые данные

-   Snapshot
-   cycle_id
-   initial_entry_prices
-   CycleSettings

------------------------------------------------------------------------

## Recovery

При восстановлении:

-   определить последний подтвержденный шаг;
-   не выполнять повторно подтвержденные операции;
-   восстановить Position и Trigger;
-   продолжить алгоритм с места остановки.

------------------------------------------------------------------------

## Использование

Данный алгоритм применяется без изменений в сценариях:

-   Scenario 2
-   Scenario 3
-   Scenario 4
-   Scenario 5
-   Scenario 6
-   Scenario 7
-   Scenario 8

Отличия этих сценариев описываются отдельно.

------------------------------------------------------------------------

## Критерии приемки

✓ Каждый Reentry подтвержден брокером.

✓ REENTRY_COSTS увеличиваются только после подтвержденного Reentry.

✓ CURRENT_TARGET рассчитывается только Formula Engine.

✓ После завершения алгоритма система готова к следующему сценарию.

Статус документа: DRAFT

# Formula Engine --- Детальная спецификация

## Назначение

Данный документ дополняет `04_FORMULA_ENGINE.md` и описывает требования
к реализации вычислений без привязки к конкретному языку
программирования.

------------------------------------------------------------------------

## Общий порядок вычислений

При каждом событии Formula Engine обязан выполнять вычисления строго в
следующем порядке:

1.  Проверить корректность входных данных.
2.  Проверить подтверждение брокера.
3.  Загрузить Snapshot.
4.  Загрузить CycleSettings.
5.  Определить текущий Scenario.
6.  Рассчитать промежуточные значения.
7.  Рассчитать итоговые TP/SL.
8.  Вернуть результаты без изменения состояния Cycle.

------------------------------------------------------------------------

## Входные данные

Formula Engine использует только подтвержденные данные:

-   реальные цены исполнения;
-   текущий Bid/Ask;
-   параметры CycleSettings;
-   накопленные REENTRY_COSTS;
-   номер сценария;
-   состояние Position.

------------------------------------------------------------------------

## Выходные данные

Возвращаются:

-   LONG Take Profit;
-   SHORT Take Profit;
-   LONG Stop Loss;
-   SHORT Stop Loss;
-   CURRENT_TARGET;
-   обновленные REENTRY_COSTS.

Formula Engine не применяет изменения самостоятельно.

------------------------------------------------------------------------

## Требования

REQ-FED-001

Все вычисления должны быть повторяемыми.

REQ-FED-002

Одинаковые входные данные всегда дают одинаковый результат.

REQ-FED-003

Любая ошибка вычислений должна возвращаться вызывающему модулю.

REQ-FED-004

Formula Engine не взаимодействует с API брокера.

------------------------------------------------------------------------

## Проверки

Перед расчетом обязательно проверить:

-   корректность цен;
-   наличие Snapshot;
-   наличие CycleSettings;
-   активность Cycle;
-   подтверждение предыдущего действия.

При невыполнении хотя бы одного условия вычисления отменяются.

------------------------------------------------------------------------

## Recovery

После восстановления Formula Engine повторяет расчет только на основании
восстановленного состояния и не использует неподтвержденные данные.

------------------------------------------------------------------------

## Критерии приемки

✓ Все вычисления выполняются централизованно.

✓ API брокера не используется.

✓ Результаты детерминированы.

✓ Ошибки корректно возвращаются вызывающему модулю.

Formula Engine --- единственный модуль проекта, имеющий право выполнять

-   учет комиссии;
-   учет проскальзывания.

------------------------------------------------------------------------

## Source of Truth

Все торговые вычисления принадлежат Formula Engine.

Ни один другой модуль не имеет права самостоятельно изменять торговые
параметры.

------------------------------------------------------------------------

## Входные данные

-   реальные цены исполнения LONG/SHORT;
-   Snapshot;
-   CycleSettings;
-   текущий Scenario;
-   накопленные REENTRY_COSTS;
-   Bid/Ask;

------------------------------------------------------------------------

## Выходные данные

-   LONG Stop Loss;
-   SHORT Stop Loss;
-   LONG Take Profit;
-   SHORT Take Profit;
-   CURRENT_TARGET;
-   REENTRY_COSTS.

------------------------------------------------------------------------

## Общие правила

REQ-FE-001

Все вычисления детерминированы.

REQ-FE-002

Одинаковые входные данные всегда дают одинаковый результат.

REQ-FE-003

Расчеты выполняются только после подтвержденных данных брокера.

REQ-FE-004

Результаты передаются Order Manager для применения.

Formula Engine обязан учитывать:

-   комиссию;

-   дополнительные настройки стратегии.

REENTRY_COSTS --- накопленная стоимость повторных входов.

При каждом подтвержденном повторном входе величина пересчитывается.

Используется при вычислении нового CURRENT_TARGET.

------------------------------------------------------------------------

## CURRENT_TARGET

CURRENT_TARGET определяет новую целевую прибыль для переоткрываемой
стороны.

Расчет выполняется после каждого подтвержденного Reentry.

## Связь со сценариями

Scenario 1: первый перерасчет.

Scenario 2--8: используется единый алгоритм перерасчета с учетом
накопленных REENTRY_COSTS.

Scenario 9: новые вычисления не выполняются до решения пользователя.

------------------------------------------------------------------------

-   отправлять команды брокеру;
-   изменять состояние Cycle;
-   создавать Trigger;

## Взаимодействие

Получает данные от: - Cycle Manager; - Snapshot; - Config.

Передает результаты: - Order Manager; - Cycle Manager.

## Обработка ошибок

Если входные данные неполные или неподтвержденные:

-   вычисления отменяются;
-   возвращается ошибка;
-   управление передается Cycle Manager.

✓ REENTRY_COSTS рассчитываются только здесь.

✓ CURRENT_TARGET рассчитывается только здесь.

✓ Другие модули не изменяют результаты Formula Engine.

# Диаграммы состояний

## Назначение

Документ определяет конечные состояния основных объектов системы и
допустимые переходы между ними.

------------------------------------------------------------------------

# Cycle

    CREATED
      ↓
    WAIT_ENTRY
      ↓
    PREPARE
      ↓
    OPENING
      ↓
    VERIFY_OPEN
      ↓
    RUNNING
      ↓
    FINISHING
      ↓
    FINISHED
      ↓
    ARCHIVED

Дополнительно из любого состояния до FINISHED допускается переход в
RECOVERY.

Запрещено: - переход через состояние; - возврат в предыдущее состояние
без Recovery.

------------------------------------------------------------------------

# Position

    CREATED
      ↓
    OPENING
      ↓
    OPEN
      ↓
    CLOSING
      ↓
    CLOSED

Дополнительно: RECOVERING --- только во время восстановления.

------------------------------------------------------------------------

# Trigger

    CREATED
      ↓
    SENT
      ↓
    CONFIRMED
      ↓
    WAITING
      ↓
    EXECUTED

или

    WAITING
      ↓
    CANCELLED

После EXECUTED и CANCELLED дальнейшие переходы запрещены.

------------------------------------------------------------------------

# Recovery

    START
      ↓
    LOAD_STATE
      ↓
    SYNC_BROKER
      ↓
    VALIDATE
      ↓
    RESTORE
      ↓
    RETURN_CONTROL

При невозможности восстановления:

    RESTORE
      ↓
    MANUAL_INTERVENTION

------------------------------------------------------------------------

## Общие правила

REQ-STATE-001

Каждый переход требует подтверждения.

REQ-STATE-002

Недопустимые переходы должны блокироваться.

REQ-STATE-003

После подтвержденного перехода обновляется last_confirmed_step.

REQ-STATE-004

Recovery продолжает выполнение только с последнего подтвержденного
состояния.

------------------------------------------------------------------------

## Критерии приемки

✓ Для каждого объекта определен конечный автомат.

✓ Все допустимые переходы описаны.

✓ Запрещенные переходы не допускаются.

✓ Recovery интегрирован в модель состояний.

# 04_TRIGGER.md

# Модель Trigger

## Назначение

Trigger представляет собой объект данных, описывающий один
Trigger-ордер, используемый для повторного входа в позицию после
подтвержденного Stop Loss.

В каждом торговом цикле одновременно допускается не более одного
активного Trigger для каждой стороны (LONG или SHORT).

------------------------------------------------------------------------

## Владелец модели

Единственный модуль, имеющий право изменять модель Trigger --- Trigger
Manager.

Другие модули могут только читать данные или получать события.

------------------------------------------------------------------------

## Основные поля

-   trigger_id
-   cycle_id
-   side (LONG / SHORT)
-   status
-   trigger_price
-   volume
-   broker_order_id
-   created_at
-   executed_at
-   cancelled_at
-   execution_price

------------------------------------------------------------------------

## Возможные состояния

CREATED

↓

SENT

↓

CONFIRMED

↓

WAITING

↓

EXECUTED

или

CANCELLED

При восстановлении допускается временное состояние:

RECOVERING

------------------------------------------------------------------------

## Правила изменения

REQ-TRG-001

trigger_id неизменяем после создания.

REQ-TRG-002

Статус изменяется только последовательно.

REQ-TRG-003

execution_price записывается только после подтверждения брокера.

REQ-TRG-004

После EXECUTED повторное исполнение запрещено.

REQ-TRG-005

После CANCELLED изменение Trigger запрещено.

------------------------------------------------------------------------

## Связь с Cycle

Каждый Trigger принадлежит одному Cycle.

Trigger не может быть перенесен в другой Cycle.

После завершения Cycle все активные Trigger должны быть отменены.

------------------------------------------------------------------------

## Связь с Reentry

После состояния EXECUTED:

-   Trigger считается завершенным;
-   Position получает повторный вход;
-   Formula Engine пересчитывает REENTRY_COSTS и CURRENT_TARGET;
-   Cycle продолжает выполнение следующего этапа.

------------------------------------------------------------------------

## Запрещено

-   создавать Trigger без подтвержденного Stop Loss;
-   изменять Trigger вручную;
-   выполнять торговые расчеты;
-   создавать второй активный Trigger для одной стороны.

------------------------------------------------------------------------

## Recovery

Recovery Manager обязан:

-   восстановить все активные Trigger;
-   сверить их состояние с брокером;
-   восстановить последнее подтвержденное состояние;
-   исключить повторное исполнение.

------------------------------------------------------------------------

## Критерии приемки

✓ Каждый Trigger принадлежит одному Cycle.

✓ Один Trigger исполняется не более одного раза.

✓ После CANCELLED Trigger неизменяем.

✓ После EXECUTED запускается логика повторного входа.

Статус документа: DRAFT

-   strategy_parameters
-   initial_scenario

------------------------------------------------------------------------

## Момент создания

Snapshot создается:

1.  После разрешения Entry Filter.
2.  До открытия LONG.
3.  До открытия SHORT.
4.  До первых расчетов Formula Engine.

------------------------------------------------------------------------

## Правила

REQ-SNP-001

Snapshot создается один раз.

REQ-SNP-002

После создания Snapshot неизменяем.

REQ-SNP-003

состояния.

REQ-SNP-004

Удаление Snapshot до архивирования Cycle запрещено.

------------------------------------------------------------------------

## Использование

Snapshot используется:

-   Recovery Manager;
-   Formula Engine;
-   Cycle Manager.

## Запрещено

-   изменять значения после создания;

-   создавать несколько Snapshot для одного Cycle.

------------------------------------------------------------------------

## Recovery

Recovery Manager обязан:

-   загрузить Snapshot;
-   проверить его целостность;
-   использовать его совместно с фактическими данными брокера;
-   восстановить состояние без изменения Snapshot.

------------------------------------------------------------------------

## Критерии приемки

✓ Snapshot создается один раз.

✓ После создания не изменяется.

✓ Recovery использует Snapshot при восстановлении.

✓ Каждый Snapshot принадлежит одному Cycle.

CREATED

SENT

CONFIRMED

WAITING

EXECUTED

# 06_CYCLE_FINISH.md

# Завершение торгового цикла

## Назначение

Документ определяет правила корректного завершения торгового цикла после
успешного выполнения стратегии или принятия решения о завершении.

------------------------------------------------------------------------

## Цель

-   завершить все торговые операции;
-   сохранить итоговое состояние;
-   сформировать Statistics;
-   архивировать Cycle;
-   подготовить систему к следующему циклу.

------------------------------------------------------------------------

## Условия начала завершения

Переход в FINISHING допускается только если:

-   активный сценарий завершен;
-   отсутствуют неподтвержденные действия;
-   Cycle Manager получил все необходимые подтверждения.

------------------------------------------------------------------------

## Последовательность

1.  Проверить отсутствие незавершенных операций.
2.  Проверить статусы Position.
3.  Проверить статусы Trigger.
4.  Сформировать Statistics.
5.  Сохранить Statistics.
6.  Перевести Cycle в FINISHED.
7.  Архивировать Cycle.
8.  Очистить временные данные.
9.  Разрешить Entry Filter запуск следующего цикла.

------------------------------------------------------------------------

## Проверки

Перед архивированием обязательно проверить:

-   все позиции имеют корректный статус;
-   активные Trigger отсутствуют;
-   Statistics успешно сохранена;
-   Snapshot сохранен;
-   журнал содержит запись о завершении.

------------------------------------------------------------------------

## Очистка

После ARCHIVED допускается очистка:

-   временных объектов;
-   рабочих кэшей;
-   внутренних структур сопровождения.

Архивные данные удалению не подлежат.

------------------------------------------------------------------------

## Recovery

Если сбой произошел во время завершения:

-   восстановить последнее подтвержденное действие;
-   продолжить процесс завершения;
-   не создавать новую Statistics повторно;
-   не архивировать Cycle повторно.

------------------------------------------------------------------------

## Запрещено

-   запускать новый Cycle до ARCHIVED;
-   изменять Statistics после сохранения;
-   изменять Snapshot;
-   выполнять новые торговые операции.

------------------------------------------------------------------------

## Критерии приемки

✓ Все операции завершены.

✓ Statistics создана один раз.

✓ Cycle архивирован.

✓ Entry Filter может начать новый цикл только после ARCHIVED.

Статус документа: DRAFT

Следующий документ: 01_CONFIG.md

# Order Manager

## Назначение

Order Manager --- единственный модуль, который имеет право отправлять
торговые команды брокеру. Все операции открытия, изменения и закрытия

------------------------------------------------------------------------

-   открытие LONG и SHORT;
-   установка и изменение Stop Loss;
-   установка и изменение Take Profit;
-   закрытие позиций;
-   отправка Trigger-команд по запросу Trigger Manager;
-   ожидание и проверка подтверждений брокера.

------------------------------------------------------------------------

## Source of Truth

Источник истины для статуса исполнения торговых команд --- Order Manager
(с обязательной синхронизацией с брокером).

------------------------------------------------------------------------

## Входные данные

-   команды Cycle Manager;
-   расчеты Formula Engine;
-   команды Trigger Manager;

-   подтверждение успешного исполнения;
-   сообщение об ошибке;
-   фактические цены исполнения;
-   идентификаторы ордеров.

------------------------------------------------------------------------

## Алгоритм выполнения

1.  Получить команду.
2.  Проверить корректность параметров.
3.  Отправить запрос через Capital API.
4.  Получить ответ брокера.
5.  Проверить статус исполнения.
6.  Зафиксировать результат.
7.  Передать подтверждение Cycle Manager.

Ни одна операция не считается завершенной до получения подтверждения

при исчерпании попыток уведомить Cycle Manager; - передать управление
Recovery Manager при необходимости.

------------------------------------------------------------------------

## Запрещено

-   выполнять торговые расчеты;
-   изменять состояние Cycle;
-   самостоятельно создавать Trigger;
-   изменять Snapshot;
-   изменять стратегию.

------------------------------------------------------------------------

## Взаимодействие

Получает: - Cycle Manager; - Formula Engine; - Trigger Manager.

Использует: - Capital API.

Передает: - подтверждения исполнения; - ошибки; - фактические цены
исполнения.

------------------------------------------------------------------------

## Обработка ошибок

При сетевой ошибке: - повторить запрос.

При ошибке API: - зафиксировать код ошибки; - выполнить повтор согласно
Retry Policy.

При отказе брокера: - уведомить Cycle Manager; - ожидать дальнейшего
решения.

------------------------------------------------------------------------

## Recovery

После перезапуска:

-   проверить открытые позиции у брокера;
-   сверить внутреннее состояние;
-   восстановить выполнение с последнего подтвержденного действия.

------------------------------------------------------------------------

## Критерии приемки

✓ Все торговые команды проходят только через Order Manager.

✓ Любая команда имеет подтверждение или ошибку.

✓ После подтверждения сохраняются реальные параметры исполнения.

✓ Order Manager не выполняет торговых расчетов.

Статус документа: DRAFT

# 07_FORMULA_EXAMPLES.md

# Примеры расчетов Formula Engine

## Назначение

Документ демонстрирует последовательность применения торговых формул.
Числовые значения используются как примеры структуры вычислений.
Окончательные формулы и параметры должны соответствовать утвержденной
стратегии.

------------------------------------------------------------------------

## Общий порядок расчета

При каждом подтвержденном событии Formula Engine:

1.  Загружает подтвержденные данные.
2.  Проверяет активный Scenario.
3.  Загружает REENTRY_COSTS.
4.  Выполняет перерасчет.
5.  Возвращает новые TP/SL и CURRENT_TARGET.

------------------------------------------------------------------------

## Пример 1. Начальный цикл

Входные данные:

-   Entry LONG = EL
-   Entry SHORT = ES
-   Stop Loss Distance = D
-   Base Target = T

Результат:

-   LONG TP = функция(EL, T)
-   SHORT TP = функция(ES, T)
-   LONG SL = функция(EL, D)
-   SHORT SL = функция(ES, D)

------------------------------------------------------------------------

## Пример 2. Первый Reentry

После подтвержденного Trigger:

REENTRY_COSTS = предыдущие REENTRY_COSTS + стоимость нового повторного
входа

CURRENT_TARGET = Base Target + REENTRY_COSTS

TP рассчитывается заново.

------------------------------------------------------------------------

## Пример 3. Последовательные Reentry

После каждого нового подтвержденного повторного входа:

REENTRY_COSTS(n) = REENTRY_COSTS(n-1) + New Reentry Cost

CURRENT_TARGET(n) = Base Target + REENTRY_COSTS(n)

Formula Engine использует только подтвержденные значения.

------------------------------------------------------------------------

## Учитываемые параметры

При вычислениях могут использоваться:

-   Spread
-   Commission
-   Slippage
-   Настройки Cycle
-   Номер Scenario

Все параметры должны быть подтверждены и документированы.

------------------------------------------------------------------------

## Общие требования

REQ-FEX-001

Все вычисления выполняются централизованно.

REQ-FEX-002

Никакой модуль не изменяет результаты Formula Engine.

REQ-FEX-003

Одинаковые входные данные дают одинаковый результат.

REQ-FEX-004

При ошибке вычислений изменения не применяются.

------------------------------------------------------------------------

## Проверка

Перед применением результатов необходимо:

-   подтвердить данные брокера;
-   подтвердить завершение предыдущего действия;
-   проверить активность Cycle.

------------------------------------------------------------------------

## Критерии приемки

✓ Формулы выполняются только Formula Engine.

✓ REENTRY_COSTS накапливаются последовательно.

✓ CURRENT_TARGET пересчитывается после каждого подтвержденного Reentry.

✓ TP/SL обновляются только после успешного расчета.

Статус документа: DRAFT

# 07_RECOVERY_MANAGER.md

# Recovery Manager

## Назначение

Recovery Manager отвечает за безопасное восстановление состояния проекта
после любого нештатного завершения работы. Его задача --- продолжить
выполнение последнего активного торгового цикла без нарушения логики
стратегии.

------------------------------------------------------------------------

## Ответственность

-   восстановление состояния Cycle;
-   восстановление Snapshot;
-   синхронизация открытых позиций с брокером;
-   синхронизация Trigger;
-   восстановление текущего Scenario;
-   возврат управления Cycle Manager.

------------------------------------------------------------------------

## Source of Truth

Источниками данных являются:

-   Snapshot;
-   сохраненное состояние Cycle;
-   актуальное состояние брокера.

------------------------------------------------------------------------

## Когда запускается

Recovery Manager активируется при:

-   перезапуске программы;
-   аварийном завершении;
-   потере соединения;
-   критической ошибке API;
-   обнаружении несогласованности состояния.

------------------------------------------------------------------------

## Алгоритм

1.  Загрузить сохраненное состояние.
2.  Проверить наличие активного Cycle.
3.  Получить текущее состояние у брокера.
4.  Сравнить локальное и фактическое состояние.
5.  Восстановить недостающие данные.
6.  Определить последнее подтвержденное действие.
7.  Передать управление Cycle Manager.

------------------------------------------------------------------------

## Основные правила

REQ-RM-001

Никогда не начинать новый Cycle, если существует незавершенный.

REQ-RM-002

Никогда не повторять уже подтвержденную торговую операцию.

REQ-RM-003

Любые расхождения должны быть зафиксированы в журнале.

REQ-RM-004

При невозможности безопасного восстановления перейти в режим ожидания
пользователя.

------------------------------------------------------------------------

## Запрещено

-   менять стратегию;
-   пересчитывать Formula Engine без запроса;
-   открывать новые позиции;
-   изменять историю завершенных циклов.

------------------------------------------------------------------------

## Взаимодействие

Получает данные от:

-   Storage;
-   Capital API;
-   Cycle Manager.

Передает результаты:

-   Cycle Manager;
-   Trigger Manager;
-   Order Manager.

------------------------------------------------------------------------

## Обработка ошибок

Если восстановление невозможно:

-   зафиксировать ошибку;
-   отправить уведомление;
-   остановить автоматическое продолжение;
-   ожидать решения пользователя.

## Критерии приемки

✓ После перезапуска незавершенный Cycle восстанавливается.

✓ Подтвержденные действия не повторяются.

✓ Состояние синхронизируется с брокером.

✓ Новый Cycle не создается до завершения восстановления.

-   Любая формула должна быть детерминированной.
-   Все вычисления выполняются только после подтверждения брокера.
-   Используются реальные цены исполнения, а не ожидаемые.

------------------------------------------------------------------------

Formula Engine получает:

-   реальные цены LONG и SHORT;
-   подтвержденные Stop Loss;
-   подтвержденные Trigger;
-   Bid / Ask;
-   Spread;
-   Commission;
-   Slippage;
-   настройки текущего Cycle;
-   накопленные REENTRY_COSTS.

1.  Проверить корректность входных данных.
2.  Определить активный Scenario.
3.  Вычислить накопленные потери.
4.  Вычислить новый CURRENT_TARGET.
5.  Рассчитать новые TP.
6.  Проверить ограничения стратегии.
7.  Передать результаты Order Manager.

# 09_STRATEGY_INVARIANTS.md

# Инварианты стратегии AI Impulse Trader

## Назначение

Документ фиксирует свойства, которые никогда не должны нарушаться.
Инварианты используются как основа для проверки реализации, тестирования
и последующих изменений проекта.

------------------------------------------------------------------------

# Инварианты цикла

INV-001

Одновременно существует только один активный Cycle.

INV-002

Новый Cycle запрещено запускать до перехода предыдущего в ARCHIVED.

INV-003

Каждый Cycle имеет один Snapshot и одну Statistics.

------------------------------------------------------------------------

# Инварианты позиций

INV-010

Каждая Position принадлежит только одному Cycle.

INV-011

LONG и SHORT сопровождаются независимо.

INV-012

Статус Position изменяется только после подтверждения брокера.

------------------------------------------------------------------------

# Инварианты Trigger

INV-020

Для одной стороны допускается только один активный Trigger.

INV-021

Исполненный Trigger не может исполниться повторно.

INV-022

После завершения Cycle активные Trigger отсутствуют.

------------------------------------------------------------------------

# Инварианты Formula Engine

INV-030

Все TP рассчитываются только Formula Engine.

INV-031

Все SL рассчитываются только Formula Engine.

INV-032

CURRENT_TARGET рассчитывается только Formula Engine.

INV-033

REENTRY_COSTS изменяются только после подтвержденного Reentry.

------------------------------------------------------------------------

# Инварианты Recovery

INV-040

Recovery не повторяет подтвержденные действия.

INV-041

Recovery не создает новый Cycle.

INV-042

После Recovery состояние совпадает с состоянием брокера.

------------------------------------------------------------------------

# Инварианты безопасности

INV-050

Любое торговое действие требует подтверждения брокера.

INV-051

Неподтвержденные изменения не применяются.

INV-052

Все критические ошибки журналируются.

------------------------------------------------------------------------

# Проверка

Каждый инвариант должен быть покрыт автоматическими тестами. Нарушение
любого инварианта считается критической ошибкой реализации.

Статус документа: DRAFT

Следующий этап: Заполнение всех математических формул и числовых
примеров на основе окончательно утвержденной стратегии.
