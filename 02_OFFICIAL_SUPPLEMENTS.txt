# SUPPLEMENT_01_SYSTEM_INVARIANTS_PART_01.md

# OFFICIAL SUPPLEMENT

**Приоритет:** выше общих архитектурных разделов проекта.

## Цель

Определить глобальные инварианты, которые обязаны соблюдаться всеми
модулями.

------------------------------------------------------------------------

## 1. Инварианты торгового движка

Во все моменты времени должны выполняться условия:

-   существует не более одного активного Cycle;
-   существует не более одного активного Scenario;
-   локальное состояние не противоречит подтвержденному состоянию
    брокера;
-   все торговые действия имеют подтверждение брокера либо находятся в
    ожидании.

------------------------------------------------------------------------

## 2. Владение состоянием

  Сущность         Единственный владелец
  ---------------- ---------------------------------------------
  Scenario         Cycle Manager
  REENTRY_COSTS    Formula Engine
  CURRENT_TARGET   Formula Engine
  Position State   Order Manager (после подтверждения брокера)
  Trigger State    Trigger Manager

Изменение сущности любым другим модулем запрещено.

------------------------------------------------------------------------

## 3. Глобальные запреты

Запрещено:

-   изменять состояние до подтверждения брокера;
-   выполнять два перехода Scenario одновременно;
-   дублировать бизнес-логику в разных модулях;
-   использовать неподтвержденные цены исполнения.

------------------------------------------------------------------------

## 4. Проверка инвариантов

После каждого подтвержденного события система обязана проверить:

-   согласованность Scenario;
-   согласованность позиций;
-   согласованность Trigger;
-   согласованность Snapshot;
-   отсутствие активного Recovery.

При нарушении любого инварианта инициируется Recovery.

------------------------------------------------------------------------

## 5. Acceptance Criteria

Проект считается соответствующим спецификации, если ни один модуль не
нарушает данные инварианты.

# SUPPLEMENT_02_CYCLE_MANAGER_PART_01.md

# OFFICIAL SUPPLEMENT

**Приоритет:** выше соответствующих разделов `02_CYCLE_MANAGER.md`.

## 1. Назначение

Cycle Manager является центральным координатором торгового движка.

Он управляет последовательностью выполнения, но не выполняет вычисления
и не обращается напрямую к брокеру.

------------------------------------------------------------------------

## 2. Единственная ответственность

Cycle Manager отвечает за:

-   создание Cycle;
-   смену Scenario;
-   запуск модулей;
-   контроль порядка выполнения;
-   завершение Cycle.

------------------------------------------------------------------------

## 3. Жизненный цикл

    READY
     ↓
    CREATE_CYCLE
     ↓
    OPEN_POSITIONS
     ↓
    RUNNING
     ↓
    FINISHING
     ↓
    ARCHIVED

Переходы выполняются только после успешного завершения предыдущего
состояния.

------------------------------------------------------------------------

## 4. Делегирование

Cycle Manager вызывает:

-   Formula Engine;
-   Order Manager;
-   Trigger Manager;
-   Recovery Manager;
-   Notification Manager.

Ни один из этих модулей не должен самостоятельно менять Scenario.

------------------------------------------------------------------------

## 5. Запрещено

Cycle Manager не имеет права:

-   выполнять математические расчеты;
-   обращаться к API брокера;
-   изменять TP/SL самостоятельно;
-   изменять REENTRY_COSTS.

------------------------------------------------------------------------

## 6. Acceptance Criteria

Реализация считается корректной, если:

-   существует только один активный Cycle;
-   Scenario изменяется только Cycle Manager;
-   последовательность состояний не нарушается;
-   все переходы журналируются.

# SUPPLEMENT_02_CYCLE_MANAGER_PART_02.md

# OFFICIAL SUPPLEMENT

**Приоритет:** выше `02_CYCLE_MANAGER.md`.

## 1. Обработка событий

Cycle Manager получает только подтвержденные события.

Допустимые события:

-   POSITION_OPEN_CONFIRMED
-   STOP_LOSS_CONFIRMED
-   TAKE_PROFIT_CONFIRMED
-   TRIGGER_EXECUTED
-   RECOVERY_COMPLETED
-   SCENARIO_COMPLETED

Неподтвержденные события игнорируются.

------------------------------------------------------------------------

## 2. Переход между Scenario

Алгоритм:

1.  Получить подтвержденное событие.
2.  Проверить активный Cycle.
3.  Проверить текущее состояние.
4.  Проверить отсутствие незавершенных операций.
5.  Увеличить номер Scenario.
6.  Сохранить Snapshot.
7.  Журналировать переход.

Запрещено изменять Scenario более чем на +1 за один переход.

------------------------------------------------------------------------

## 3. Интеграция с Recovery

Если любой модуль сообщает о неизвестном состоянии:

-   приостановить выполнение;
-   передать управление Recovery Manager;
-   дождаться RECOVERY_COMPLETED;
-   продолжить с последнего подтвержденного состояния.

------------------------------------------------------------------------

## 4. Журналирование

Для каждого перехода сохраняются:

-   Cycle ID;
-   Scenario;
-   событие-инициатор;
-   время;
-   результат проверки;
-   новое состояние.

------------------------------------------------------------------------

## 5. Инварианты

-   Только один активный Cycle.
-   Только один активный Scenario.
-   Все переходы последовательны.
-   Любое критическое расхождение переводит систему в Recovery или
    Scenario 9.

------------------------------------------------------------------------

## 6. Acceptance Criteria

Cycle Manager реализован корректно, если:

-   отсутствуют пропущенные состояния;
-   отсутствуют параллельные переходы;
-   все переходы выполняются только после подтверждения брокера;
-   после Recovery выполнение продолжается с последнего подтвержденного
    состояния.

# SUPPLEMENT_03_UNIVERSAL_REENTRY_PART_01.md

# OFFICIAL SUPPLEMENT

**Приоритет:** выше соответствующих разделов `03_UNIVERSAL_REENTRY.md`.

## Цель

Настоящее дополнение устраняет неоднозначности алгоритма Reentry и
определяет обязательный порядок действий для реализации в Codex.

------------------------------------------------------------------------

## 1. Предусловия Reentry

Reentry допускается только если одновременно выполнены условия:

-   Stop Loss подтвержден брокером;
-   активный Cycle существует;
-   Trigger еще не создан для данной позиции;
-   Recovery не выполняется.

Если хотя бы одно условие ложно --- Reentry запрещен.

------------------------------------------------------------------------

## 2. Алгоритм

1.  Получить событие `STOP_LOSS_CONFIRMED`.
2.  Зафиксировать цену исполнения Stop Loss.
3.  Передать управление Trigger Manager.
4.  Создать Trigger на первоначальной цене входа закрытой позиции.
5.  Дождаться подтверждения брокера.
6.  Перевести Trigger в состояние WAITING.
7.  После события `TRIGGER_EXECUTED` передать управление Formula Engine.
8.  Выполнить перерасчет.
9.  Передать новые параметры Order Manager.

------------------------------------------------------------------------

## 3. Обязательные проверки

После каждого подтвержденного Reentry необходимо проверить:

-   увеличился REENTRY_COUNT;
-   обновился REENTRY_COSTS;
-   пересчитан CURRENT_TARGET;
-   рассчитан новый Take Profit;
-   Snapshot обновлен после подтверждения брокера.

------------------------------------------------------------------------

## 4. Инварианты

-   Одновременно существует не более одного активного Trigger для одной
    стороны.
-   Один Trigger соответствует одному подтвержденному Stop Loss.
-   Повторный Reentry без подтверждения брокера запрещен.

------------------------------------------------------------------------

## 5. Recovery

Если Trigger исполнен, но локальное состояние отличается от брокера:

1.  Остановить дальнейшие действия.
2.  Выполнить синхронизацию.
3.  Повторно определить состояние.
4.  Продолжить только после полного совпадения.

------------------------------------------------------------------------

## 6. Требования для Codex

Запрещается:

-   создавать Reentry по локальному предположению;
-   увеличивать REENTRY_COUNT без подтверждения;
-   изменять REENTRY_COSTS вне Formula Engine;
-   пропускать этап проверки после Trigger.

# SUPPLEMENT_03_UNIVERSAL_REENTRY_PART_02.md

# OFFICIAL SUPPLEMENT

**Priority:** Higher than the corresponding sections of
`03_UNIVERSAL_REENTRY.md`.

## 1. Mathematical relationship

Every confirmed Reentry creates exactly one new compensation increment.

    Confirmed Reentry
            ↓
    Increase REENTRY_COUNT
            ↓
    Calculate new REENTRY_COST
            ↓
    REENTRY_COSTS += REENTRY_COST
            ↓
    Recalculate CURRENT_TARGET
            ↓
    Recalculate TP

No other event may change REENTRY_COSTS.

------------------------------------------------------------------------

## 2. Scenario progression

Scenario transitions are sequential only.

    1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 9

Skipping a scenario is prohibited.

------------------------------------------------------------------------

## 3. Compensation rules

For every confirmed Reentry:

-   preserve previous accumulated compensation;
-   append the newly confirmed compensation;
-   never overwrite historical values.

The accumulated value always represents the total confirmed compensation
of the current Cycle.

------------------------------------------------------------------------

## 4. Broker confirmation

Only after broker confirmation:

-   increment REENTRY_COUNT;
-   update Snapshot;
-   update Statistics;
-   continue to Formula Engine.

Pending or assumed execution must never modify state.

------------------------------------------------------------------------

## 5. Edge Cases

### Trigger executed twice

Treat as critical inconsistency. Stop processing and start Recovery.

### Trigger cancelled by broker

Do not continue the scenario. Synchronize state.

### Trigger missing

Do not recreate automatically until broker state is verified.

------------------------------------------------------------------------

## 6. Logging

For every Reentry write:

-   Scenario;
-   Trigger ID;
-   Position ID;
-   Entry price;
-   Execution price;
-   REENTRY_COUNT;
-   REENTRY_COSTS before;
-   REENTRY_COSTS after;
-   CURRENT_TARGET.

------------------------------------------------------------------------

## 7. Acceptance Criteria

Implementation is accepted only if:

-   one confirmed Trigger produces one confirmed Reentry;
-   REENTRY_COSTS is monotonic during a Cycle;
-   all updates are broker-confirmed;
-   Recovery can restore the latest confirmed state without changing
    history.

# SUPPLEMENT_04_FORMULA_ENGINE_PART_01.md

# OFFICIAL SUPPLEMENT
**Приоритет:** ВЫШЕ соответствующих разделов `04_FORMULA_ENGINE.md`.

Настоящий документ уточняет требования для реализации в Codex.

---

## 1. Цель Formula Engine

Formula Engine является **единственным модулем**, который имеет право выполнять
математические расчеты стратегии.

Он **не имеет права**:
- обращаться к API брокера;
- открывать или закрывать позиции;
- создавать Trigger;
- изменять состояние Cycle;
- изменять Snapshot напрямую.

---

## 2. Единственный источник входных данных

Formula Engine использует только подтвержденные данные:

- Broker Confirmation;
- Snapshot;
- Cycle State;
- Config;
- Scenario Number.

Неподтвержденные локальные значения запрещено использовать в расчетах.

---

## 3. Владение переменными

| Переменная | Владелец | Изменяется |
|------------|----------|------------|
| CURRENT_TARGET | Formula Engine | После подтвержденного Reentry |
| REENTRY_COSTS | Formula Engine | После подтвержденного Reentry |
| REENTRY_COUNT | Cycle Manager | После подтверждения Trigger |
| LONG_ENTRY_PRICE | Order Manager | Один раз |
| SHORT_ENTRY_PRICE | Order Manager | Один раз |

Другие модули могут только читать эти значения.

---

## 4. Конвейер вычислений

1. Проверить активный Cycle.
2. Проверить подтверждение брокера.
3. Получить Snapshot.
4. Получить Scenario.
5. Проверить входные данные.
6. Рассчитать REENTRY_COSTS.
7. Рассчитать CURRENT_TARGET.
8. Рассчитать новые TP.
9. Выполнить математическую валидацию.
10. Вернуть результат Order Manager.

---

## 5. Инварианты

Всегда должны выполняться правила:

- Formula Engine детерминирован.
- Одинаковые входные данные дают одинаковый результат.
- Все расчеты используют Decimal.
- Все расчеты журналируются.
- Никакое состояние не изменяется до подтверждения брокера.

---

## 6. Требования для Codex

При реализации запрещено:
- размещать формулы в Order Manager;
- выполнять расчеты в Trigger Manager;
- изменять TP вне Formula Engine;
- дублировать математическую логику в других файлах.

Все вычисления должны быть сосредоточены в одном модуле Formula Engine.

# SUPPLEMENT_04_FORMULA_ENGINE_PART_02.md

# OFFICIAL SUPPLEMENT

**Приоритет:** выше соответствующих разделов `04_FORMULA_ENGINE.md`.

## 1. Назначение

Данное дополнение определяет обязательную математическую модель Formula
Engine.

Codex обязан реализовать вычисления в указанном порядке.

------------------------------------------------------------------------

## 2. Порядок вычислений

Каждый перерасчет выполняется строго по цепочке:

1.  Проверить подтверждение брокера.
2.  Определить текущий Scenario.
3.  Получить подтвержденные цены исполнения.
4.  Определить активную позицию.
5.  Обновить REENTRY_COSTS.
6.  Рассчитать CURRENT_TARGET.
7.  Рассчитать новый Take Profit.
8.  Выполнить проверку ограничений.
9.  Передать результат Order Manager.

Пропуск шагов запрещен.

------------------------------------------------------------------------

## 3. REENTRY_COSTS

REENTRY_COSTS --- накопленная сумма затрат, подлежащая компенсации.

Содержит:

-   подтвержденные убытки от повторных входов;
-   комиссии;
-   проскальзывание;
-   дополнительные издержки, если они утверждены стратегией.

Увеличивается только после подтвержденного исполнения Reentry.

------------------------------------------------------------------------

## 4. CURRENT_TARGET

CURRENT_TARGET рассчитывается Formula Engine.

Общая структура:

    CURRENT_TARGET =
    BASE_TARGET
    + REENTRY_COSTS
    + ADDITIONAL_TARGET

Где:

-   BASE_TARGET --- базовая цель цикла;
-   REENTRY_COSTS --- накопленные подтвержденные затраты;
-   ADDITIONAL_TARGET --- дополнительная прибыль (если включена в
    настройках).

------------------------------------------------------------------------

## 5. Правила перерасчета

Formula Engine обязан пересчитать CURRENT_TARGET после:

-   подтвержденного Trigger;
-   подтвержденного Reentry;
-   изменения накопленных затрат.

Изменение рыночной цены само по себе перерасчет не вызывает.

------------------------------------------------------------------------

## 6. Валидация

Перед передачей результата необходимо проверить:

-   TP расположен по правильную сторону от цены входа;
-   значения соответствуют ограничениям брокера;
-   отсутствуют отрицательные компенсации;
-   все обязательные входные данные присутствуют.

При любой ошибке результат не применяется.

------------------------------------------------------------------------

## 7. Требования для Codex

Запрещается:

-   хранить дублирующие формулы в других модулях;
-   изменять CURRENT_TARGET вне Formula Engine;
-   использовать неподтвержденные цены исполнения.

Formula Engine является единственным источником математических
вычислений стратегии.

# SUPPLEMENT_04_FORMULA_ENGINE_PART_03.md

# OFFICIAL SUPPLEMENT

**Приоритет:** выше соответствующих разделов `04_FORMULA_ENGINE.md`.

## 1. Recovery Formula Engine

Recovery не пересчитывает значения автоматически.

Последовательность:

1.  Загрузить Snapshot.
2.  Получить подтвержденное состояние брокера.
3.  Сверить входные данные.
4.  Проверить REENTRY_COUNT.
5.  Проверить REENTRY_COSTS.
6.  Повторно вычислить CURRENT_TARGET.
7.  Сравнить результат с сохраненным состоянием.
8.  При совпадении вернуть управление Cycle Manager.

При несовпадении перейти в безопасный режим и остановить автоматическое
выполнение.

------------------------------------------------------------------------

## 2. Edge Cases

### Отсутствует цена исполнения

Расчет запрещен.

### Trigger подтвержден, но позиция отсутствует

Запустить Recovery.

### Получено неполное подтверждение брокера

Ожидать повторного подтверждения. Никаких вычислений не выполнять.

### Отрицательное значение REENTRY_COSTS

Считать критической ошибкой.

------------------------------------------------------------------------

## 3. Журналирование

Каждый запуск Formula Engine обязан записывать:

-   время расчета;
-   номер Scenario;
-   входные параметры;
-   REENTRY_COUNT;
-   REENTRY_COSTS;
-   CURRENT_TARGET;
-   рассчитанные TP;
-   итог проверки.

------------------------------------------------------------------------

## 4. Псевдокод

``` text
Receive Confirmed Event
↓

Validate Input
↓

Load Snapshot
↓

Update REENTRY_COSTS
↓

Calculate CURRENT_TARGET
↓

Calculate Take Profit
↓

Validate Result
↓

Return Calculation
```

------------------------------------------------------------------------

## 5. Acceptance Criteria

Formula Engine считается реализованным корректно, если:

-   все расчеты детерминированы;
-   одинаковые входные данные дают одинаковый результат;
-   отсутствуют обращения к API;
-   отсутствует изменение состояния Cycle;
-   все расчеты выполняются только после подтверждения брокера.

------------------------------------------------------------------------

## 6. Типичные ошибки реализации

Codex не должен:

-   выполнять вычисления в Order Manager;
-   рассчитывать TP в Trigger Manager;
-   изменять математические значения в Recovery;
-   использовать неподтвержденные данные;
-   дублировать формулы в нескольких файлах.

# SUPPLEMENT_04_SCENARIOS_02_08_PART_01.md

# OFFICIAL SUPPLEMENT

**Приоритет:** выше соответствующих разделов `04_SCENARIOS_02_08.md`.

## Цель

Уточнить обязательное поведение сценариев 2--8 для реализации в Codex.

------------------------------------------------------------------------

## Общие правила

Каждый новый сценарий начинается **только** после полного завершения
предыдущего.

Обязательные условия перехода:

-   брокер подтвердил последнее действие;
-   Snapshot обновлен;
-   CURRENT_SCENARIO увеличен на 1;
-   отсутствуют незавершенные операции.

------------------------------------------------------------------------

## Универсальный алгоритм сценария

1.  Получить подтвержденное событие.
2.  Проверить активный Cycle.
3.  Проверить Scenario.
4.  Выполнить действие сценария.
5.  Дождаться подтверждения брокера.
6.  Обновить Snapshot.
7.  Передать управление Formula Engine.
8.  Выполнить перерасчет.
9.  Перейти к следующему состоянию.

------------------------------------------------------------------------

## Изменение переменных

После подтвержденного Reentry:

-   REENTRY_COUNT = REENTRY_COUNT + 1
-   REENTRY_COSTS обновляется Formula Engine.
-   CURRENT_TARGET пересчитывается.
-   TP активной позиции пересчитывается.
-   LONG_ENTRY_PRICE и SHORT_ENTRY_PRICE не изменяются, если повторный
    вход не создал новую подтвержденную позицию.

------------------------------------------------------------------------

## Запрещено

-   переходить сразу к Scenario 4 из Scenario 2;
-   изменять номер сценария без подтверждения брокера;
-   выполнять два сценария одновременно;
-   пересчитывать TP до подтверждения Reentry.

------------------------------------------------------------------------

## Recovery

Если во время сценария обнаружено расхождение между локальным состоянием
и брокером:

1.  Приостановить сценарий.
2.  Выполнить синхронизацию.
3.  Определить последнее подтвержденное действие.

-   сохранить цену;

После события TRIGGER_EXECUTED:

1.  получить подтвержденную цену исполнения;

При отмене Trigger:

-   изменять Scenario.

------------------------------------------------------------------------

## 7. Acceptance Criteria

-   Один Trigger соответствует одному Stop Loss.
-   Повторная обработка Trigger невозможна.
-   Все изменения подтверждены брокером.
-   Все события Trigger журналируются.

Recovery обязан различать:

Для любого активного Scenario:

1.  Определить последнее подтвержденное действие.
2.  Получить текущее состояние брокера.
3.  Определить текущий Scenario.
4.  Проверить REENTRY_COUNT.
5.  Проверить REENTRY_COSTS.
6.  Восстановить только подтвержденные данные.

-   причину;
-   время начала;

-   время завершения;
-   итоговый статус.

------------------------------------------------------------------------

-   API недоступно → оставаться в Recovery.
-   Snapshot отсутствует → использовать подтвержденные данные брокера.

------------------------------------------------------------------------

## 5. Acceptance Criteria

Recovery считается завершенным только если:

-   локальные данные совпадают с брокером;
-   Snapshot восстановлен;
-   журнал сохранен;
-   автоматическая торговля безопасна;
-   Cycle может быть продолжен без нарушения истории.

# SUPPLEMENT_11_GLOSSARY_PART_01.md

# OFFICIAL SUPPLEMENT

**Приоритет:** выше общих определений проекта.

## Цель

Настоящий документ вводит единый словарь терминов. Все модули и весь код
должны использовать только эти определения.

------------------------------------------------------------------------

## Основные термины

### Cycle

Полный торговый цикл, начинающийся с открытия стартовых позиций и
заканчивающийся завершением стратегии либо переходом в Scenario 9.

------------------------------------------------------------------------

### Scenario

Подтвержденное состояние текущего этапа Cycle.

Изменяется только Cycle Manager.

------------------------------------------------------------------------

### Broker Confirmation

Подтверждение от брокера о фактическом выполнении операции.

Только после него допускается изменение локального состояния.

------------------------------------------------------------------------

### Trigger

Отложенный ордер повторного входа.

Существует в единственном экземпляре для соответствующей стороны.

------------------------------------------------------------------------

### Snapshot

Сохраненное подтвержденное состояние Cycle.

Используется только для Recovery и проверки согласованности.

------------------------------------------------------------------------

### Recovery

Процесс восстановления локального состояния до полного соответствия
состоянию брокера.

Recovery не является частью торговой стратегии.

------------------------------------------------------------------------

### CURRENT_TARGET

Текущая цель прибыли, рассчитываемая только Formula Engine.

------------------------------------------------------------------------

### REENTRY_COSTS

Накопленная подтвержденная сумма компенсации текущего Cycle.

Изменяется только Formula Engine.

------------------------------------------------------------------------

## Требования для Codex

Во всех классах, комментариях и документации использовать только
определения из данного словаря.

Запрещается вводить альтернативные названия для уже определенных
терминов.

------------------------------------------------------------------------

## Acceptance Criteria

Все модули используют одинаковые определения терминов и не содержат
противоречащих трактовок.

# SUPPLEMENT_18_PERFORMANCE_STANDARD_PART_01.md

# OFFICIAL SUPPLEMENT

**Приоритет:** выше общих требований производительности.

## 1. Назначение

Торговый движок должен сохранять предсказуемое время выполнения
независимо от номера Scenario.

------------------------------------------------------------------------

## 2. Основные требования

-   отсутствие бесконечных циклов;
-   отсутствие блокирующих ожиданий без тайм-аута;
-   минимизация повторных запросов к брокеру;
-   все операции журналирования выполняются без изменения торговой
    логики.

------------------------------------------------------------------------

## 3. Ограничения

Каждый модуль обязан:

-   выполнять только свою ответственность;
-   освобождать временные ресурсы после завершения операции;
-   не хранить устаревшие объекты после завершения Cycle.

------------------------------------------------------------------------

## 4. Масштабируемость

Архитектура должна позволять в будущем:

-   добавить новые брокеры;
-   добавить новые инструменты;
-   добавить новые каналы уведомлений;

без изменения ядра Formula Engine.

------------------------------------------------------------------------

## 5. Требования для Codex

Оптимизация не должна изменять бизнес-логику.

Сначала корректность, затем производительность.

------------------------------------------------------------------------

## 6. Acceptance Criteria

Проект соответствует требованиям, если увеличение количества завершенных
Cycle не приводит к накоплению неиспользуемых объектов и не требует
изменения архитектуры.

# SUPPLEMENT_19_SECURITY_STANDARD_PART_01.md

# OFFICIAL SUPPLEMENT

**Приоритет:** выше общих разделов безопасности.

## 1. Назначение

Настоящий документ определяет обязательные требования безопасности для
торгового движка.

------------------------------------------------------------------------

## 2. Конфиденциальные данные

Запрещено хранить в открытом виде:

-   API Key;
-   Refresh Token;
-   Access Token;
-   пароли;
-   секретные ключи.

------------------------------------------------------------------------

## 3. Журналирование

Запрещается записывать в журнал:

-   полные токены;
-   пароли;
-   секретные ключи.

Допускается журналировать только маскированные значения.

------------------------------------------------------------------------

## 4. Проверка доступа

Перед каждой торговой операцией необходимо проверить:

-   действительность авторизации;
-   доступность счета;
-   разрешение на торговлю.

------------------------------------------------------------------------

## 5. Требования для Codex

Все секреты должны поступать через единый механизм конфигурации.

Ни один модуль не должен содержать встроенные учетные данные.

------------------------------------------------------------------------

## 6. Acceptance Criteria

Система соответствует требованиям, если секретные данные не попадают в
код, логи или сообщения об ошибках и могут быть безопасно заменены без
изменения исходного кода.

# SUPPLEMENT_20_IMPLEMENTATION_ORDER_PART_01.md

# OFFICIAL SUPPLEMENT

**Приоритет:** обязательный для реализации Codex.

## 1. Цель

Настоящий документ определяет единственный рекомендуемый порядок
разработки проекта.

Codex не должен начинать реализацию высокоуровневых модулей до
завершения базовых компонентов.

------------------------------------------------------------------------

## 2. Порядок реализации

Этап 1 --- Foundation

-   Config Manager
-   Logger
-   Event Bus
-   Data Models
-   Exceptions

Этап 2 --- Core

-   Cycle Manager
-   Formula Engine
-   Trigger Manager
-   Order Manager
-   Recovery Manager

Этап 3 --- Broker

-   Capital API
-   Synchronization
-   State Persistence

Этап 4 --- Strategy

-   Universal Reentry
-   Scenarios 1--9
-   Notification Manager

Этап 5 --- Testing

-   Unit Tests
-   Integration Tests
-   Recovery Tests
-   End-to-End Simulation

------------------------------------------------------------------------

## 3. Правила

Следующий этап начинается только после успешного завершения предыдущего.

Не допускается реализация бизнес-логики до готовности базовой
архитектуры.

------------------------------------------------------------------------

## 4. Definition of Done

Этап считается завершенным только если:

-   код проходит тесты;
-   документация обновлена;
-   журналирование реализовано;
-   инварианты соблюдены.

------------------------------------------------------------------------

## 5. Acceptance Criteria

Результирующий проект должен быть построен последовательно, без
циклических зависимостей между модулями.

# SUPPLEMENT_21_DIRECTORY_STRUCTURE_PART_01.md

# OFFICIAL SUPPLEMENT

**Приоритет:** обязательный для реализации Codex.

## 1. Цель

Определить рекомендуемую структуру проекта и исключить хаотичное
размещение файлов.

------------------------------------------------------------------------

## 2. Структура каталогов

    ai_impulse_trader/
    ├── config/
    ├── core/
    ├── broker/
    ├── formula/
    ├── recovery/
    ├── events/
    ├── models/
    ├── notifications/
    ├── persistence/
    ├── strategy/
    ├── simulator/
    ├── tests/
    ├── logs/
    └── docs/

------------------------------------------------------------------------

## 3. Правила размещения

-   Один модуль --- одна папка.
-   Запрещено смешивать бизнес-логику и инфраструктуру.
-   Документация хранится отдельно от исходного кода.
-   Тесты не размещаются внутри рабочих модулей.

------------------------------------------------------------------------

## 4. Зависимости

Разрешенное направление зависимостей:

-   strategy → core
-   core → models
-   broker → models
-   recovery → core
-   tests → все публичные интерфейсы

Запрещены циклические зависимости.

------------------------------------------------------------------------

## 5. Требования для Codex

При создании новых файлов использовать существующую структуру.

Если требуется новый каталог, он должен иметь единственную
ответственность и быть описан в документации.

------------------------------------------------------------------------

## 6. Acceptance Criteria

Структура считается корректной, если:

-   каждый файл имеет логичное место;
-   отсутствуют циклические зависимости;
-   модули можно тестировать независимо;
-   архитектура допускает расширение без реорганизации каталогов.

# SUPPLEMENT_22_DEPENDENCY_GRAPH_PART_01.md

# OFFICIAL SUPPLEMENT

**Приоритет:** обязательный для реализации Codex.

## 1. Цель

Определить допустимые зависимости между модулями и запретить нарушения
архитектуры.

------------------------------------------------------------------------

## 2. Разрешенный граф зависимостей

    Config
       ↓
    Models
       ↓
    Event Bus
       ↓
    Cycle Manager
       ├──→ Formula Engine
       ├──→ Trigger Manager
       ├──→ Order Manager
       ├──→ Recovery Manager
       └──→ Notification Manager

    Order Manager
          ↓
    Capital API
          ↓
    Broker

------------------------------------------------------------------------

## 3. Запрещенные зависимости

Запрещается:

-   Formula Engine → Broker API
-   Formula Engine → Notification Manager
-   Capital API → Formula Engine
-   Models → Broker API
-   Recovery → Formula Engine (изменение вычислений)
-   Notification Manager → Order Manager

------------------------------------------------------------------------

## 4. Правило направленности

Каждый модуль знает только о публичных интерфейсах нижележащих модулей.

Обратные зависимости запрещены.

------------------------------------------------------------------------

## 5. Проверка архитектуры

Перед добавлением новой зависимости необходимо проверить:

-   не возникает ли циклическая зависимость;
-   не нарушается ли принцип единственной ответственности;
-   не появляется ли дублирование логики.

------------------------------------------------------------------------

## 6. Acceptance Criteria

Архитектура считается корректной, если:

-   отсутствуют циклические зависимости;
-   каждый модуль имеет минимально необходимое число связей;
-   бизнес-логика сосредоточена только в предназначенных для этого
    модулях.

# SUPPLEMENT_23_FINAL_RULES_FOR_CODEX_PART_01.md

# OFFICIAL SUPPLEMENT

**Статус:** ОБЯЗАТЕЛЬНО ДЛЯ ИСПОЛНЕНИЯ CODEX

## Цель

Настоящий документ определяет финальные правила, которым Codex обязан
следовать при реализации проекта.

------------------------------------------------------------------------

## 1. Приоритет документации

При конфликте требований используется следующий порядок:

1.  OFFICIAL SUPPLEMENT
2.  Основная документация
3.  Комментарии в коде

------------------------------------------------------------------------

## 2. Запрещается

-   изменять математическую модель Formula Engine;
-   переносить бизнес-логику в API;
-   изменять владельцев состояния;
-   нарушать System Invariants;
-   создавать циклические зависимости;
-   игнорировать подтверждение брокера.

------------------------------------------------------------------------

## 3. Обязательные требования

Перед реализацией каждого модуля:

-   изучить связанную документацию;
-   реализовать публичный интерфейс;
-   добавить журналирование;
-   добавить обработку ошибок;
-   добавить тесты.

------------------------------------------------------------------------

## 4. Definition of Done

Модуль считается завершенным только если:

-   реализован полностью;
-   соответствует документации;
-   проходит тесты;
-   не нарушает архитектуру;
-   интегрируется с остальными модулями.

------------------------------------------------------------------------

## 5. Финальная проверка

Перед завершением проекта необходимо убедиться:

-   отсутствуют TODO/FIXME;
-   отсутствуют заглушки;
-   отсутствует дублирование бизнес-логики;
-   все зависимости соответствуют Dependency Graph;
-   все инварианты соблюдены.

------------------------------------------------------------------------

## 6. Acceptance Criteria

Проект считается завершенным только если весь исходный код соответствует
основной документации и всем OFFICIAL SUPPLEMENT без исключений.
